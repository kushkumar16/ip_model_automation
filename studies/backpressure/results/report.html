Backpressure Study

How FIFO depth, response-handler latency, issue rate, flow-control delay and latency variance decide whether a request/response pipeline keeps its throughput or stalls back to the source.

What the runs show

1 / slowestthroughput ceiling

Throughput never exceeded the slowest stage's rate. FIFO depth decides how close to that ceiling you get when latencies vary. It never moves the ceiling. See load and handler.

18 → 105 cycleslatency cliff

With a constant handler, raising handler_latency from 10 to 10.5 cycles (just past the 10-cycle issue interval) filled both FIFOs. Median latency jumped from 18 to 105 cycles, and the requester was stalled 5% of the time. Past that point, the latency is roughly the total buffering (8 entries) times the handler period.

8.5% → 0.8%responder stall, exp handler

An exponential handler at 70% load stalled the responder 8.5% of the time with a response FIFO of depth 1, 0.8% at depth 4, and 0% at depth 8. A bimodal (heavy-tail) handler at the same mean needed depth 12–16. It lost 6% throughput at depth 1. A constant handler needed no FIFO at all.

depth ≈ B − Tburst/Tsvcburst sizing

With the drop policy, a burst of B back-to-back requests needed a request FIFO of about B minus the requests served during the burst. At burst length 16, depth 12 still lost 12.5% of requests; depth 16 lost none.

depth / Lcreditcredit loop cap

With credit flow control, throughput matched min(offered, depth / credit_return_latency) exactly. A depth-2 FIFO with a 32-cycle credit loop ran at 62.5% of offered load, even though every stage was fast enough.

λ × loaded RTToutstanding cap

Size max_outstanding using the loaded round trip, not the unloaded one. At 10 cycles per request the unloaded round trip is 14 cycles, which suggests 2 are enough. In practice 2 reached only 72% of offered load, and it took 6–8 to reach the uncapped result.

depth moves loss into latencytrade-off

A deeper FIFO turns stalls or drops into queueing delay. For the exponential responder, going from depth 4 to 16 raised throughput from 93% to 99.8% of offered load. The cost was p99 latency, which rose from 91 to 167 cycles.

Experiment 1 · issue rate

Offered load against throughput and latency

Where does the pipeline saturate, and what happens to latency on the way there?

Reading it. Poisson arrivals with exponential service and handler times. With depth 2, the pipeline delivered only 87% of the offered 0.1 req/cycle, well below saturation. That is because a blocked requester loses its issue slots. Depth 16 held 99.8% at the same load, but p99 latency rose from 82 to 169 cycles.

Rule. Choose depth for the lowest utilization at which you need full throughput. Then accept that latency grows with depth once the offered rate is close to the slowest stage's rate.

Experiment 2 · response handler latency

A slow handler stalls every stage upstream

When the response handler is the slowest stage, how far back does the stall travel?

Reading it. The constant handler shows a hard cliff. At 10 cycles it has no effect. At 10.5, both FIFOs sit full, the responder is blocked 24% of the time and the requester 5%. The exponential handler degrades gradually instead: at 9 cycles (90% handler utilization) it already loses 1.7% of throughput and its p99 latency is 131 cycles.

Rule. Keep handler utilization below about 85% when handler latency varies. Buffering cannot fix a mean handler rate that is too slow; it only delays the point where the stall reaches the source.

Experiment 3 · response FIFO depth

Response FIFO depth against handler jitter

How deep must the response FIFO be to keep a jittery handler from stalling the responder?

Reading it. All handler distributions have the same 7-cycle mean. Constant and uniform (±50%) handlers never back up, so depth 1 is enough. The exponential handler needs depth 4–8. The bimodal handler (10% of responses take 5.5× the mean) needs 12–16. For the bimodal handler, p99 latency hardly changes with depth, because the slow responses set the tail.

Rule. Size the response FIFO for the handler's latency variance, not its mean. Measure the handler's p99 service time and cover the responses that arrive during it.

Experiment 4 · issue burstiness

Absorbing bursts without dropping requests

How much request FIFO does a bursty source need before it stops losing requests?

Reading it. The average rate is well inside capacity (80% responder utilization), yet a shallow FIFO drops up to 81% of the requests in a 32-request burst. The responder handles about one request per 8 cycles during a burst. Losses therefore stop once depth is about B − B/8: depth 4 for B=4, 8 for B=8, 16 for B=16, and 32 for B=32 (the next depth tested).

Rule. Size the request FIFO for the longest burst: B − B·gap/service. Under the block policy, a FIFO that is too shallow stalls the source instead of dropping requests.

Experiment 5 · flow-control delay

Credit return latency against request FIFO depth

How does a slow credit return limit throughput for each FIFO depth?

Reading it. Every stage is fast enough, and the request FIFO is empty on average. The limit is the credit loop: each credit makes one trip per credit_return_latency, so throughput is capped at depth / L. Depth 2 hits the cap at L = 20. Depth 4 hits it at L = 40. Depth 8 and 16 never hit it in this range.

Rule. Choose credit-based FIFO depth ≥ issue_rate × credit round trip, including pipeline stages on the return path. This is a bandwidth-delay product, not a buffering requirement.

Experiment 6 · outstanding requests

How many requests must be in flight

How many requests must be allowed in flight to reach full rate?

Reading it. By Little's law, the in-flight count equals throughput × round trip. The unloaded round trip is 14 cycles, but with queueing it is about 33 cycles at 0.1 req/cycle, so about 3.3 requests are in flight on average. Variance pushes the practical requirement to 6–8. Beyond that, the cap has no effect and the FIFO depths set the limit.

Rule. Size max_outstanding ≥ offered rate × p90 loaded round trip. Use a smaller value on purpose if you need to bound latency.

Experiment 7 · responder latency variance

Same mean, different spread

With the mean fixed, what does latency spread alone cost?

Reading it. At depth 4, going from a constant to a bimodal responder cost 9.5 points of throughput (97.7% → 88.2%). The mean was the same in both cases, and the responder was only 80% utilized. Depth 16 recovered the throughput, but p99 latency rose to 200 cycles.

Rule. When latency has a tail, add depth where the tail occurs. Track p99 latency and stall fraction, not just the mean.

Method and limits

  • Model: studies/backpressure/backpressure_sim.py. Runs: run_study.py, with results in results/study_results.csv.
  • Latency is measured from when the requester tried to issue, so time the source spends stalled counts toward it. A blocked requester does not make up missed slots (it is a stalling source, not a source with an unbounded queue).
  • Responder workers may complete out of order. There is no reorder buffer and no arbitration between several requesters. The ready signal is instant unless flow_control=credit.
